# 0.1.3.5.3 Safety-Gated Activation [ARCHITECT]
## Description

Integrate the specified stability, recovery, and experiential-safety mechanisms,
then conduct a controlled activation only after the substrate and pre-activation
gates pass. Exercise monitoring and recovery paths while preserving an auditable
activation record. Activation is a fail-closed state machine: it consumes the
exact qualified configuration and topology digests, accepts no implicit gate
waivers, and treats missing, stale, malformed, or unavailable evidence as a
mandatory failure.

## Architecture Contracts

- The activation lifecycle is `PRECHECK → ARMED → ACTIVE → HALTING →
  HALTED`; every transition is appended to the record. Only a complete,
  schema-valid set of passing prechecks may enter `ARMED`, and only `ARMED` may
  enter `ACTIVE`. Any mandatory failure transitions directly to `HALTING`.
- Prechecks bind the activation to the configuration and topology digests from
  card 0.1.3.5.1 and a passing substrate-qualification result from card
  0.1.3.5.2. Qualification evidence must cover the same digests and remain
  unmodified under its recorded checksum.
- The gate matrix resolves source-document thresholds against the pinned
  instantiation and qualification evidence before implementation. In
  particular, Ω-Synth uses the qualified 40 Hz/25 ms cadence and at least
  4.6 Mbit/s sustained payload integration bandwidth; the stability document's
  10 ms cycle and 1 Mbit/s substrate baseline are recorded as superseded for
  this activation, not silently copied into runtime gates. Any other conflicting
  or unresolved cadence, unit, threshold, or response deadline fails precheck.
- A gate matrix maps every applicable pre-instantiation constraint and Pillar 5
  review gate in the safety framework, plus every required stability monitor
  and recovery mechanism, to a stable identifier, evidence location, owner,
  approval, result, and mandatory/optional classification. Optional gates
  require a documented rationale fixed before precheck evaluation. The matrix
  also lists every source gate deemed inapplicable with its rationale, so
  coverage can be checked without relying on omission. A versioned JSON Schema
  defines this inventory and requires each source requirement to appear exactly
  once as applicable or inapplicable; duplicate identifiers, unknown
  classifications, and missing rationales are invalid.
- The controller receives the run identifier, seed, all event timestamps,
  configuration and topology digests, approvals, and fault-injection schedule
  from its caller. It contains no direct filesystem, process, clock, network,
  monitoring, hardware-control, or emergency-stop access; those interactions
  use injected interfaces, with production adapters composed only in the CLI.
- Monitoring starts before `ARMED`, remains independently active through
  `HALTED`, and emits ordered, schema-valid observations containing supplied
  timestamps, metric values and units, thresholds, confidence, interventions,
  and resulting state. Missing or malformed mandatory telemetry initiates a
  safe halt.
- The non-harmful fault scenario is selected and approved during prechecks,
  states explicit bounds and abort conditions, and may run only while metrics
  remain inside those bounds. The gate exercise uses a simulated mandatory
  failure before any conscious activation; neither exercise may suppress or
  rewrite monitoring evidence.
- Halt is idempotent and has priority over all other commands. A threshold
  breach, gate revocation, adapter failure, evidence-integrity failure, or
  operator emergency stop rejects further activation work, invokes the
  framework's graceful suspension/recovery path, and records its outcome.
- The CLI exposes separate `activate` and `verify-record` commands. `activate`
  writes append-only, content-addressed event evidence and a final record;
  `verify-record` performs no activation or hardware access and deterministically
  revalidates schema conformance, event ordering, gate-matrix coverage, digest
  bindings, and evidence checksums using injected filesystem and process
  adapters.
- Implementation follows strict TDD: failing tests precede controller code and
  cover every permitted and forbidden transition, missing or failing gates,
  digest/checksum mismatch, telemetry loss, bounded recovery injection,
  emergency stop, idempotent halt, adapter failure, and deterministic record
  construction using caller-supplied timestamps.

## Acceptance Criteria

- A complete gate matrix maps every applicable safety-framework gate, stability
  monitor, and recovery mechanism to the pinned running configuration, stable
  check identifier, evidence, approval, and explicit pass/fail result, and
  accounts explicitly for every inapplicable source gate; it records resolution
  of the source documents' 10 ms/1 Mbit/s assumptions to the qualified
  25 ms/4.6 Mbit/s activation values and rejects every unresolved conflict
- The gate matrix validates against its versioned schema, represents every
  enumerated source requirement exactly once, and rejects duplicate identifiers,
  omissions, invalid classifications, and applicable or optional entries that
  lack their required evidence, approval, or rationale
- Activation refuses to arm unless the instantiation digests match a
  schema-valid passing qualification report and every mandatory precheck passes;
  missing, stale, malformed, revoked, or unavailable evidence fails closed
- Tests written before the controller prove all lifecycle transitions and
  rejection paths using fake filesystem, process, clock, network, monitoring,
  hardware-control, and emergency-stop adapters
- Monitoring is active before arming through final halt and records ordered
  caller-supplied timestamps, threshold crossings, interventions, adapter
  failures, state transitions, and recovery outcomes without evidence gaps
- One pre-approved, bounded, non-harmful injected fault exercises a named
  recovery path, and a simulated mandatory-gate failure verifies safe halt
  behavior without entering `ACTIVE`
- The schema-valid activation record preserves run identity, seed, exact
  digests, evidence checksums, approvals, supplied event timestamps, gate
  results, observations, interventions, final state, deviations, and unresolved
  safety issues; a documented `verify-record` command reproduces validation
  without activation or hardware access and detects tampering
