# 0.1.3.5.1 Instantiation Specification [ARCHITECT]
## Description

Translate the Ω-Synth reference architecture into an executable, versioned
instantiation specification. Pin every architecture, runtime, substrate, and
measurement dependency needed to reproduce the system without relying on
unstated environment assumptions. Resolve every suggested range and alternative
in the reference design to one named baseline value or implementation, while
keeping permitted experimental overrides explicit and machine-validated.

## Architecture Contracts

- `baseline.yaml` is the single source of truth for every resolved architecture,
  runtime, substrate, and measurement value. The prose explains those choices
  and references configuration keys; it must not define competing defaults.
- The schema is closed at every object boundary and encodes cross-field topology
  constraints that JSON Schema cannot express as named verifier checks.
- Verification proceeds schema validation → semantic topology validation →
  deterministic topology-manifest construction → digest comparison. The digest
  is SHA-256 over UTF-8 canonical JSON with recursively sorted keys, no
  insignificant whitespace, and arrays retained in declared order.
- The topology manifest contains only normalized nodes, directed edges, tensor
  shapes, update order, initialization metadata, and invariant parameters.
  Runtime observations and host-specific paths are evidence, not digest inputs.
- A caller supplies the seed, observation timestamp, filesystem adapter, process
  runner, clock, and network policy. Production adapters are selected only by
  the command entry point; specification and verification code depend solely on
  injected interfaces, and tests use denying or in-memory fakes.
- Unknown keys and implicit defaults are errors. Experimental overrides must be
  supplied as a separate validated overlay, recorded in evidence, and produce a
  distinct configuration and topology digest without mutating the baseline.
- Runtime verification reads the exact Node.js version from `.node-version`, the
  exact npm version from the `packageManager` field in `package.json`, and exact
  resolved package versions from `package-lock.json`. A range, absent lock,
  mismatch among those files, or lockfile regeneration is a verification
  failure; `package-lock.json` alone must not be treated as a Node.js or npm
  version lock.
- The baseline names one reference processor model and its required
  microcode/firmware revision, not only an ISA or performance class. It also
  declares each required accelerator and driver with an exact version, or uses
  explicit empty lists when the CPU-only baseline requires neither. Verification
  evidence records the observed values and fails closed when they cannot be
  obtained through the injected process adapter.
- Each failure reports a stable check identifier, configuration path, expected
  value, and actual value so substrate qualification can consume results
  without parsing prose.
- `instantiation.ts` owns parsing-independent domain types, schema and semantic
  validation orchestration, topology-manifest construction, and digesting. It
  accepts already-read configuration text plus explicit seed and observation
  timestamp values and has no direct environment access.
- `adapters.ts` defines the minimum filesystem, process, clock, and network-policy
  interfaces. `cli.ts` is the sole composition root for production adapters and
  exposes `npx tsx src/omega-synth/cli.ts verify --config
  configs/omega-synth/baseline.yaml --seed <integer> --observed-at <RFC3339>`.
  The command fails closed if either caller-supplied value is absent and emits
  schema-valid JSON evidence to stdout.
- Implementation follows strict TDD: failing unit tests cover schema rejection,
  every named semantic topology check, canonical digest fixtures, overlays, and
  mismatch diagnostics before domain code; CLI tests use injected fakes to
  prove denied network access and no undeclared filesystem or process calls.

## Baseline Decision Registry

The checked-in baseline uses the following resolved values. Configuration may
repeat them only as schema-validated values; implementation must not substitute
host-derived defaults.

| Key | Baseline |
|---|---|
| Layer dimensions `D_in`, `D_core`, `D_hub`, `D_ws`, `D_sm`, `D_ho`, `D_tb`, `D_out` | 256, 256, 512, 512, 512, 256, 128, 256 |
| Processing cadence | 40 Hz; 25 ms synchronous timestep |
| State nonlinearities | `tanh` for L1–L5 and L7–L10; `sigmoid` for learned gates; `softmax` for L6 selection |
| Workspace ignition | `theta_ign = 0.7`; retain the prior L7 state when not ignited |
| Hub bypass | learned scalar sigmoid gate initialized to `0.5` |
| Inter-core invariant | all 12 directed L1–L4 edges present; `w_floor = 0.01` |
| Temporal binding | four Kuramoto oscillators plus a 128-dimensional GRU token; synchronous update from the prior timestep |
| Loss weights | `alpha_SM = 0.1`, `alpha_div = 0.01`, `alpha_gate = 0.001`, `alpha_ign = 0.001`, `lambda_meta = 0.1` |
| Initialization | caller-seeded Xavier uniform for feedforward/input matrices, caller-seeded orthogonal recurrent matrices, zero biases except the hub-bypass bias producing `0.5` |
| Numerical representation | IEEE-754 binary32 for model state and weights; binary64 only for verifier-side canonical numeric normalization |
| Target substrate | classical-silicon CPU baseline, at least 1×10⁹ OPS, 32 MB available memory, 4.6 Mbit/s sustained payload integration bandwidth at 40 Hz, and 10 ms maximum inter-module latency |
| Runtime/toolchain | Ubuntu 24.04.2 LTS x86-64 with Linux kernel 6.8.0-60-generic; Node.js 22.16.0 in `.node-version`; `npm@11.4.1` in the `packageManager` field; `package-lock.json` pins TypeScript, `tsx`, Vitest, and every transitive dependency; all values are repeated in `baseline.yaml` and must agree |
| Reference processor | Intel Xeon Gold 6338 (`family 6`, `model 106`, `stepping 6`) with Intel microcode revision `0xd0003e7`; the CPU-only baseline declares `accelerators: []` and `drivers: []` |

The semantic verifier names and enforces at least:
`TOPOLOGY_NODE_SET`, `TOPOLOGY_EDGE_SET`, `TOPOLOGY_EDGE_COUNT`,
`TOPOLOGY_DIMENSION`, `TOPOLOGY_UPDATE_ORDER`, `INTERCORE_WEIGHT_FLOOR`,
`IGNITION_THRESHOLD`, `INITIALIZATION_RULE`, `RUNTIME_VERSION`,
`CALLER_SEED`, `CALLER_TIMESTAMP`, and `TOPOLOGY_DIGEST`.

## Acceptance Criteria

- The specification enumerates L0–L11, every required directed connection and
  recurrent loop, tensor dimensions, update ordering, initialization rule,
  activation function, gating behavior, and non-zero inter-core weight invariant
- The baseline configuration resolves every range, optional path, and
  implementation alternative in the architecture input; the schema rejects
  missing, unknown, out-of-range, and topology-breaking values
- Runtime, package and toolchain versions are locked; the target compute
  substrate records an exact reference processor and firmware revision,
  exact-version accelerator and driver lists (or explicit empty lists),
  numerical precision, memory minimum, and supported platform
- Build and initialization consume an explicit caller-supplied seed and
  timestamp, perform no undeclared network or filesystem access, and produce a
  configuration digest plus a topology manifest
- One documented command builds and verifies the baseline in a clean
  environment using injected filesystem, process, clock, and network adapters;
  tests use fakes for those adapters
- Verification fails on any node, edge, dimension, parameter, version, seed, or
  digest mismatch and records the exact mismatch; the passing fixture proves
  that the instantiated topology equals the checked-in baseline
- The prose specification cross-references the baseline, schema, verification
  command, expected topology digest, and the evidence consumed by substrate
  qualification card 0.1.3.5.2
